# CafeLauncher Web Runner (development)

This is the local runner for the optional web-action flow. It targets Windows PowerShell 5.1 and .NET Framework already present on supported Windows café PCs; it adds no runtime package. The web page currently exposes **Apply profile**, **Apply game graphics**, and **Play + Exec** for one selected profile. The runner also retains Detect PC compatibility for older clients and diagnostics. It verifies a `cafe.bat` release and invokes only the requested allowlisted action. Runner v0.7.0 forwards local action-stage progress and elapsed times to the web page while the action is running. Runner v0.7.3 accepts a stable, schema-checked final result file and closes a lingering PowerShell host if it does not exit on its own. Runner v0.7.4 reports safe timeout diagnostics (result-file state and last local stage) in the action result; launcher progress now separates settings completion, result construction, JSON serialization, and result-file writing so a future stall identifies its exact boundary. The runner also keeps a small rolling local log at `%LOCALAPPDATA%\CafeLauncher\Runner\logs\runner.log` for runner startup, result-file detection, timeout, and backend final-result delivery; it omits action IDs, tokens, and result contents.

## Build

From this directory, run:

```powershell
.\Build-WebRunner.ps1
```

The script uses the .NET Framework C# compiler and writes `build\CafeLauncherWebRunner.exe` by default. The website download link points to the latest GitHub Release asset. The player opens the downloaded executable once: it copies itself to `%LOCALAPPDATA%\CafeLauncher\Runner\CafeLauncherWebRunner.exe`, verifies the copied bytes, registers `cafelauncher://` for that Windows account, and adds a per-user installed-app entry so Windows can recognize that setup completed. This needs no admin rights. Setup also caches the pinned Logitech helper at `%LOCALAPPDATA%\CafeLauncher\logihub\logihub.exe` after checking its SHA-256. If setup has no network access, the runner still installs and retries before the next Apply Profile action. Windows can then remove the runner from the current user's Installed apps list; it removes the protocol registration and self-deletes after its process exits. After that bootstrap, each web action checks the immutable GitHub runner release manifest and silently installs a newer runner side-by-side when available; the action continues through the new version without asking the player to open another download. Before Apply Profile starts the launcher, the runner rechecks and repairs a missing or incorrect helper cache, reporting that preparation as its own timed progress stage. A transient GitHub connection failure leaves the installed runner usable, while a hash/size mismatch blocks execution. If a different protocol handler is already registered, setup stops instead of replacing it. `--register` and `--unregister` remain available for staff provisioning; unregister removes the key only when it still points to this executable.

The app cannot be installed silently by a browser. On a PC where user files survive reboot, the download-and-open step is a one-time setup for that Windows account. If Deep Freeze or another reset discards LocalAppData or the registry at reboot, café staff must install/register it in the saved base image or reprovision it during maintenance. If the runner is reinstalled from an older frozen image, it self-updates again on the first web action. A player download cannot make a reset-protected installation persistent.

## Request safety

- Accepts exactly one URI matching `cafelauncher://v1/run/<43-character-base64url-id>`.
- The URI carries no action name, profile, command, path, or script.
- Claims through the HTTPS backend with a fresh random capability; an ambiguous claim retry reuses that capability.
- Downloads only the latest immutable launcher artifact from the pinned backend origin, validates the same-origin release path, size, SHA-256, and embedded release marker, then caches it by release version under the current user's LocalAppData.
- If that backend artifact predates the requested web action, fetches the current `cafe.bat` from the fixed Cs-script GitHub Contents API endpoint, verifies the reported size and Git blob SHA-1, checks the release marker and action entry point, then caches it under a SHA-addressed LocalAppData folder. This avoids opening the old dashboard/updater just to upgrade to web-action support.
- Runs the verified launcher's embedded PowerShell in a separate Windows PowerShell process with a fixed action context. No URI text is passed to PowerShell as a command or script argument.
- Runner setup caches the pinned Logitech helper and verifies its SHA-256. Before Web Apply Profile, the runner checks that cache again and repairs a missing or mismatched file, then reports the setup stage separately before starting Windows profile changes. The launcher retains the same pinned hash check and verifies the live DPI read-back; it does not write mouse onboard memory. After the runner first upgrades, a one-time marker causes local pending profile edits to be replaced with verified primary-backend snapshots for all affected profiles; if any snapshot cannot be verified, the action stops and the pending edits remain. The marker is cleared after this reset succeeds, so later local edits are not discarded automatically.
- Keeps the result capability in process memory and uploads bounded structured events. Local stages report a running update and a completion update with elapsed seconds. Progress uploads are best-effort and do not stop the local action if the web connection fails. No browser sync token is used.
- Web Apply Profile skips the configured app-launch step so it cannot start FACEIT Anti-Cheat, Steam, or other profile apps. The normal Windows launcher behavior remains unchanged.
- Polls a capability-protected backend control endpoint while the local PowerShell action runs. A stop received before the launcher starts reports `CANCELED`; stopping a live PowerShell process reports `INTERRUPTED` because some settings may already have changed. Network loss can delay or prevent a stop request from reaching the runner.
- The web result panel downloads a local text report from the action timeline. It includes progress events and result steps but omits raw local paths and device data; the report is not automatically uploaded.

## Current limits

- The protocol is registered for the current Windows account on this workstation. Its reboot and Deep Freeze persistence have not been tested on a café PC.
- The runner's first-run self-install copies it under the current account's LocalAppData and registers the protocol. `tools/Test-WebRunnerInstall.ps1` exercises initial copy, same-version no-op, and replacement using temporary test files only.
- `tools/Test-WebRunnerCompatibility.ps1` checks GitHub blob verification, requested-action support detection, tampered-payload rejection, and refusal to cache a Logitech helper with the wrong pinned SHA-256 using synthetic data only.
- The backend web-action API is deployed and configured. Its latest immutable launcher artifact may predate web-action support; the runner's GitHub-verified fallback fetches the current launcher source when required. Existing installed runners check for a newer verified runner when a web action starts and can update without another manual download when GitHub is reachable.
- Play + Exec requires an active Steam session, a uniquely detected CS2 CFG path, no unresolved local profile edits, and a current primary-backend profile/graphics/CFG history bundle. It fails closed on a backend rollback or unavailable snapshot and does not silently use mirror or local fallback data.
- CFG writes use the detected path pinned at the start of the action, revalidated immediately before each install. If a write or Steam launch may have happened but no complete result is available, the runner reports `INTERRUPTED`; the web page stays locked until the player confirms they checked the PC.
- Deep Freeze persistence, protocol activation, real Steam/CS2 discovery, Logitech device behavior, and the web result round trip remain unverified on a café PC. Automated checks use mocks and synthetic release metadata; they do not claim physical device verification.
